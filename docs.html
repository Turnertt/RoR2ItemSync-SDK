PART 1 The essentials read this, build your app

TL;DR#

The whole protocol in 30 seconds. If you remember nothing else from these docs, this is the part that matters.

What this is

RoR2ItemSync is a Risk of Rain 2 mod that runs inside the game and exposes the player's live run state as JSON over a localhost WebSocket. Your app connects, listens for messages, and optionally asks the mod for things. There's nothing else to install — every modern language has a WebSocket client.

Two ports

PortProtocolWhat it's for
11420WebSocket (TCP)The actual protocol. Your app connects here.
11421UDP (multicast + broadcast)Auto-discovery. The mod responds to DISCOVER packets and sends a passive beacon every 2s with its IP and port. Optional — you can skip discovery entirely and connect directly to 127.0.0.1:11420.

How the conversation works

  1. You open a WebSocket to ws://127.0.0.1:11420/
  2. The mod sends you a hello message with its version and a list of every command it supports
  3. You can send requests like {"type": "ping"} and get tagged responses back
  4. You can listen for broadcasts like inventory_update (every 500ms by default while in a run) and lifecycle events (run_started, stage_changed, player_died, pickup_granted, run_ended)
  5. Every message is JSON with a type field for discrimination and a schema_version field for forward compatibility

The smallest possible app

This is a working companion app. It connects, says hi, and prints every message:

pythonimport json, websocket

ws = websocket.create_connection("ws://127.0.0.1:11420/")
while True:
    print(json.loads(ws.recv()))

Or the same thing in browser JavaScript (paste in DevTools console):

jsconst ws = new WebSocket("ws://127.0.0.1:11420/");
ws.onmessage = e => console.log(JSON.parse(e.data));

Things to know before you start

  • No authentication. By default the mod binds to all network interfaces, so anyone on the same machine or LAN can connect. (The host can restrict this to localhost-only in config.) Treat the feed as trusted local-network data — don't expose it to the public internet.
  • At title screen / character-select you get nothing automatic. No inventory_update, no events. Send {"type": "request_world_state"} if you want a snapshot of the current (probably empty) state.
  • Reconnects can catch up via the run journal. The mod records every notable event in memory for the current run. After a brief disconnect, send {"type": "request_run_journal"} to replay everything you missed, then request_world_state for current truth. See Run journal & reconnect. Over the protocol you can only query the current/last run — older runs aren't retrievable. (The host can optionally export each finished run to a local .jsonl file, but that's a host-side recording, not something your app fetches over the WebSocket.)
  • sequence gaps are normal. The mod's sequence counter is shared across all connected clients. Other clients' responses consume sequence numbers your session never sees. Don't treat gaps as missed messages.
  • Rate limits exist. They're per client and per request type — request_world_state and request_run_journal at 1/sec, the two bulk catalogs slower. Over-limit requests get an error reply with retry_after_ms, not silence. See the limit table.
  • Feature-detect, don't hardcode. The hello message's capabilities array lists every supported command. Check it before sending anything specific — if a future mod version adds new events, your app stays compatible automatically.
  • Two schema versions ship side by side. The real-time stuff is schema_version: 2 (live). The bulk metadata catalogs (modded items, achievements) are schema_version: 1 (dump). Both are documented below.

Quickstart#

RoR2ItemSync runs inside Risk of Rain 2 and exposes the player's live run state over a localhost WebSocket. Companion apps can show inventory, stage, stats, pickups, and modded item metadata without scraping the game UI.

The mod listens on ws://127.0.0.1:11420/. When you connect, the server sends:

  1. A hello message — mod version, schema, supported commands
  2. The last cached inventory_update (if there is one)

After that it pushes events as they happen and replies to requests you send.

JavaScript (browser console)#

Paste this into the DevTools console while Risk of Rain 2 is running with the mod loaded:

jsconst ws = new WebSocket("ws://127.0.0.1:11420/");
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  console.log(msg.type, msg);
};
// Send a ping after we're connected
ws.onopen = () => ws.send(JSON.stringify({ type: "ping" }));

You'll see a hello, possibly an inventory_update, and a pong.

shellpip install websocket-client

A slightly bigger example#

Capture the next inventory_update and print the local player's items:

pythonimport json
import websocket

ws = websocket.create_connection("ws://127.0.0.1:11420/")

# Force an immediate snapshot rather than waiting for the next broadcast tick
ws.send(json.dumps({"type": "request_world_state"}))

while True:
    msg = json.loads(ws.recv())
    if msg["type"] != "inventory_update":
        continue
    print(f"Stage {msg['stage']['number']}: {msg['stage']['name']}")
    for player in msg["players"]:
        if not player["is_local"]:
            continue
        print(f"  {player['display_name']} as {player['survivor']['name']}")
        for item in player["items"]:
            print(f"    {item['count']}x {item['name']} ({item['tier']})")

Building your app: the loop#

Every robust companion app follows the same pattern:

  1. Connect to ws://127.0.0.1:11420/ (or discover via UDP — see UDP discovery)
  2. Wait for hello, check schema_version, read capabilities
  3. Send request_world_state to get an immediate snapshot
  4. Consume broadcasts (inventory_update, lifecycle events) as they arrive
  5. Send requests when you need more (request_run_summary, request_loadout, etc.)
  6. Reconnect with backoff if the socket closes

Feature detection#

The mod's hello.capabilities lists every supported message type. Feature-detect against this rather than hardcoding — if a new event lands in v2.1, your v2.0-targeted app stays compatible.

jsconst supports = new Set(hello.capabilities);

if (hello.schema_version !== 2) {
  console.warn(`Unknown schema_version ${hello.schema_version} — proceed with caution`);
}

if (supports.has("request_loadout")) {
  ws.send(JSON.stringify({ type: "request_loadout" }));
}

Also: ignore unknown fields on messages you do handle. The mod adds fields additively within a schema version.

The essentials#

Handle these two and you have a complete, correct companion app.

helloYour first message — mod version + the capability list. Read it, then forget it.

Exampleexamples/hello.json

The very first message you get when you connect. It tells you the mod's version, how often it broadcasts, and — most importantly — the full list of commands this mod supports. Read that list instead of hardcoding, and your app keeps working as the mod grows.

{
    "type": "hello",
    "schema_version": 2,
    "timestamp": "...", "sequence": 1, "state": "menu", "run_id": "",
    "mod_name": "RoR2ItemSync",
    "mod_version": "2.0.0",
    "ror2_version": "1.4.1",
    "broadcast_intervals": { "inventory_update_ms": 500, "world_scan_ms": 5000 },
    "capabilities": [ "inventory_update", "ping", "request_world_state", "..." ]
  }

hello is always the first message. After it, the server may immediately send the last cached inventory_update if one exists.

Use it for:
  • Confirming the mod is alive and checking its version
  • Feature-detecting which commands exist before you send them (capabilities)
  • Reading the broadcast cadence from broadcast_intervals instead of hardcoding 500ms

Exampleexamples/inventory_update.json

The heartbeat of the protocol. Twice a second during a run (the default 500ms cadence), the mod sends the complete current state — every player, their items, stats and gold, the stage, the difficulty, and what's left to loot. If you build around one message, build around this one.

      "equipment_barrels_remaining": 0,
      "shop_items":    [ ItemRef ],
      "printer_items": [ ItemRef ],
      "ground_items":  [ ItemRef ],
      "command_items": [{ "tier": "Tier1" }],
      "minions": {
        "total": 2,
        "by_owner": [
          {
            "owner_network_user_id": "76561198...",
            "owner_display_name":    "ExamplePlayer",
            "count": 2,

              {

              },
              {
                "body_name": "EquipmentDroneBody",
                "name":  "Equipment Drone",

      }

  }

At title screen / character-select (state ≠ "in_run"), broadcasts don't fire — you only see this from a request_world_state reply.

world.minions is a snapshot of player-owned minions on the stage — drones, turrets, beetle guards, wisps, and so on — grouped by the owning player's network_user_id (which matches a PlayerRecord), with one bots[] entry per live bot: two Gunner Drones are two entries. Each entry carries the bot's identity (body_name + localized name), live vitals (stats — health / max_health / shield / barrier / is_alive), and its own items array using the exact ItemRef/EquipRef shapes players carry: Engineer turrets copy their owner's items, equipment drones hold their equipment, Spare Drone Parts grants show up, and most combat drones are just []. Only live minions (with a spawned body) owned by a player are listed; enemy minions are excluded. Unlike the rest of the payload this is refreshed on the world-scan cadence (hello.broadcast_intervals.world_scan_ms, 5s by default), not every tick — so a bot's health bar and item list can lag a beat behind live combat. A bot's own events (e.g. a turret triggering a pickup_granted) carry player.owner_network_user_id so you can attribute them to the same human without joining against this list.

world.teleporter is the live teleporter state, read fresh every tick (unlike the scan-cadence counts above it): state is RoR2's ActivationState verbatim (Idle / IdleToCharging / Charging / Charged / Finished), charge_fraction is the holdout zone charge 0..1 (smooth enough at the broadcast cadence for a charge ring), and is_charging / is_charged are conveniences. null when the scene has no teleporter (menus, Bazaar, Void Fields). world.boss mirrors the in-game boss health bar — same name / subtitle and the same combined current/max health aggregated across the boss group — and is null whenever no boss bar is showing. Both are additive v2 fields; older clients that ignore unknown keys are unaffected.

The timer field carries raw RoR2 stopwatch values. is_paused is derived from actual stopwatch behavior — true whenever run_seconds isn't advancing (pause menu, Bazaar, focus-loss auto-pause, dev console, cutscenes). Broadcasts keep firing at the broadcast cadence throughout — including while the game window is unfocused. See Timer behavior for monotonicity, the has_focus pairing, and the recommended extrapolation pattern.

Use it for:
  • A live inventory grid and stat panel — the core of most overlays
  • A gold / economy tracker
  • A multiplayer party view, one card per player
  • Anything that needs "the current state of the run, right now"

Run timeline events (optional)#

The narrative beats of a run, in order. Add these for a kill-feed, timeline, or Discord announcer. All carry severity: "major".

run_startedA new run began — clear last run's UI.

run_started

DirectionServer → client (broadcast)
Sent whenA new run begins
Capabilityrun_started
Exampleexamples/run_started.json

A brand-new run just began. This is your cue to clear last run's UI and start fresh — the run_id is a new one, and the message carries the run's identity card: seed, game mode, difficulty, artifacts.

{
    "type": "run_started",
    "schema_version": 2,
    "severity": "major",
    "timestamp": "...", "sequence": 100,
    "state": "in_run",
    "run_id": "9c4a8e1f...",
    "seed": "13959349961389347880",   // ulong as a STRING (2^53 JSON precision)
    "game_mode": "ClassicRun",        // internal name verbatim
    "difficulty": Difficulty,
    "eclipse_level": 0,               // 1-8 on Eclipse, 0 otherwise
    "artifacts": [{ "id": "Command", "name": "Artifact of Command" }],
    "player_count": 1
  }

Apps reset run-scoped UI here. run_id is the fresh GUID for the new run, and this is always the first entry in the run journal — which makes the journal's opening line a self-describing run record. Two field notes: seed is a decimal string (it's a 64-bit value; JSON numbers lose precision above 253), and game_mode is RoR2's internal mode name verbatim ("ClassicRun", "InfiniteTowerRun" for Simulacrum, "EclipseRun", "WeeklyRun" for Prismatic Trials) — pass unknown values through. player_count counts player slots at run start; the full roster (survivors + skills) arrives moments later as the journal's loadout_response entry.

Use it for:
  • Clearing last run's UI and counters
  • Starting a fresh timeline or run log
  • Tagging everything that follows with the new run_id

DirectionServer → client (broadcast)
Sent whenEvery member of a BossGroup is dead (encounter end)
Capabilityboss_defeated

The stage's boss fight is over — every boss in the encounter is dead. You get one event for the whole fight, even when there were several bosses, with a count of each type.

{
    "type": "boss_defeated",
    "schema_version": 2,
    "severity": "major",
    "timestamp": "...", "sequence": 612,
    "state": "in_run",
    "run_id": "9c4a8e1f...",
    "timer":  Timer,
    "stage":  Stage,

No player block — boss defeats credit the encounter, not an individual. The teleporter_charged event fires before this when the holdout finishes; pair the two to time the boss fight (boss_defeated.timer.run_seconds − teleporter_charged.timer.run_seconds).

Use it for:
  • A "boss defeated" celebration moment
  • Logging which bosses a run faced
  • Boss-kill timing stats (pair with the teleporter events)

A player just died — and killed_by says what got them. In most runs this is the end, but with revive mechanics (like Dio's Best Friend) a player can die more than once — so don't assume one death means game over.

{
    "type": "player_died",
    "schema_version": 2,
    "severity": "major",

    "player": Player,
    "killed_by": {

      "body_name": "GolemBody",      // monster/player kinds only
      "name":      "Stone Titan",
      "is_elite":  false
    },
    "timer":  Timer,
    "stage":  Stage

Only fires for player-controlled bodies. Monsters and drones do not fire this. A player can die multiple times in a run if revived via Dio's Best Friend or extra-life mechanics — pair with player_respawned. killed_by.kind values:

monsterAn enemy. DoT deaths (burn, bleed) attribute to whoever applied the DoT; a kill by an enemy-owned minion attributes to the minion's own body.
playerAnother player (Artifact of Chaos friendly fire). Carries the attacker's body fields, not their Steam identity.
fallFall damage. No attacker fields.
unknownNo attacker and not a fall — void fog, map hazards, sourceless mod damage. No attacker fields. Treat unrecognized future kind values like this.

Use it for:
  • A death notification / toast in your overlay
  • Marking deaths on the run timeline
  • Counting deaths per player in co-op

outcome — how the run finished

This is the field a run history sorts, filters and badges on. Without it a win, a wipe on stage 3 and an alt-F4 are indistinguishable.

"completed"A winning ending (ending.is_win is true). The standard escape, Obliteration, killing the Voidling and so on are all wins — read ending.name to tell them apart.
"defeated"A losing ending — the party died out.
"quit"The player left a live run (quit to menu). RoR2 raises no game-over for this, which is precisely how it's detected: no ending by teardown time means nobody finished. ending is null.
"unknown"A game over fired but carried no ending. Shouldn't occur in vanilla; treat as "ended, outcome unavailable". ending is null.

Closing the game mid-run sends nothing There is no run_ended with outcome: "quit" when the process exits — the game is gone before it could send one. That case is only visible host-side, as a journal file ending in a run_summary with no run_ended. If your app persists runs, treat "a run that never got a run_ended" as abandoned rather than assuming it's still live.
Use it for:
  • Showing an end-of-run recap (time survived, items, deaths)
  • Saving the run to history before the journal is wiped
  • Returning your overlay to its idle / menu state

Run journal & reconnect#

The run journal is the mod's in-memory record of every notable event in the current (or most recently finished) run. It's the primary tool for seamless reconnect: a companion app that briefly disconnects can rebuild its view of the run without the user noticing. Timeline visualizations, per-stage stats, and replay UIs all fall out of the journal for free.

Core rules#

  • Mod-owned run state, not session state. The journal records events even when no WebSocket clients are connected. Connect mid-run and you can immediately fetch everything that happened before you arrived.
  • Lifecycle. Cleared at run_started (so the new run's run_started is the first entry); frozen at run_ended; remains queryable until the next run_started wipes it.
  • Ring buffer. Capped at 10,000 entries. When full, oldest entries are dropped from the head — late-run reconnects still get the most recent ~10k events. The response carries metadata so your app knows whether and how much it lost.
  • More than events. Journal-only entry kinds round the journal out into a complete, self-contained run record: a loadout_response right after run_started (the opening roster — who's playing which survivor with which skills), state snapshots (full inventory_update copies stamped severity: "snapshot" — periodic every 30s by default plus boundary snapshots at each stage start, at game over, and a final one at run end — the exact final build when run state is still readable at teardown (always the case for death/victory via the game-over capture), else a reissue of the last live capture), run_summary stat sheets on the same cadence and with the same "snapshot" severity (kills/damage/deaths so far — stat progression over time), and a final run_summary (no severity) just before run_ended. None of these are re-broadcast — live clients already have the equivalent data.
  • Snapshots are excluded from responses by default. They're full state payloads, so a reconnect catch-up doesn't pay for them unless it opts in — set include_snapshots: true (or name "snapshot" in severities). For current state after a reconnect, request_world_state remains the right call.
  • Disk streaming (host-side, on by default). The host streams every journal entry to a local .jsonl file as it happens — one file per run, one JSON object per line, flushed per line, so a crash mid-run keeps everything up to the crash. Snapshots are always included on disk, making the file a replayable record of the whole run. Closing the game mid-run appends one last run_summary before the file is closed — so a file that ends with a run_summary and no run_ended is the "game was closed mid-run" signature. This is purely a host-side recording — it isn't exposed over the protocol, so your app can't request those files remotely. If you need cross-run history in your app, record it yourself as events arrive.

Reconnect pattern#

The canonical mid-run reconnect flow. For socket-level concerns — backoff timing, what survives a reconnect, what doesn't get redelivered — see Reconnection strategy in the appendix.

  1. Open WebSocket → receive hello. Verify capabilities includes request_run_journal.
  2. Send request_run_journal with since_sequence = the last sequence your app processed (or omit on first connect). The response carries every journaled event since.
  3. Send request_world_state for the authoritative current snapshot.
  4. Reconcile: journal = history, inventory_update = current truth. Both rate limits are independent — back-to-back is fine.
  5. Resume from live broadcasts.

If the response shows history_truncated: true and oldest_sequence > since_sequence, the ring buffer dropped some early-run history before you could fetch it. Display "partial run history" or treat the run as un-rebuildable depending on UX.

Connecting#

Connection options#

MethodUse whenHow
Direct connectApp and game on the same machine, or you already know the host's IPConnect to ws://<host>:11420/

Both end up with a normal WebSocket connection — discovery is just a way to learn the IP and port.

Host-side config matters The person running the mod can change several things from their BepInEx config, so build defensively:
  • Ports aren't fixed. 11420 / 11421 are defaults. Don't hardcode them — discover via UDP, or read the port from the beacon payload.
  • Broadcast cadence varies. Default is 500ms, but it's tunable (100–5000ms). Read hello.broadcast_intervals.inventory_update_ms instead of assuming.
  • The server may be localhost-only. Default is LAN-reachable, but a host can bind to loopback — then only apps on the same machine can connect, and discovery is off.
  • Discovery may be disabled. Always support direct connect as a fallback; don't rely solely on the beacon.
The full list of host settings lives in the mod's README. None of them change the wire format — only where/how often the data flows.

UDP discovery#

The mod exposes discovery on UDP port 11421. Apps can either send an active DISCOVER packet for an immediate response, or listen for the passive beacon the mod broadcasts every 2 seconds.

Response / beacon payload

Both active replies and passive beacons use the same UTF-8 text payload, single line, no terminator:

ROR2SYNC:<host_ip>:<websocket_port>:<mod_version>

Example:

ROR2SYNC:192.168.1.42:11420:2.0.0
FieldMeaning
ROR2SYNCFixed magic prefix — apps should verify this before parsing
<host_ip>The host's local IP. Apps connect to this.
<websocket_port>The WebSocket server port. Defaults to 11420 but the host can change it — always use this field rather than assuming a port.
<mod_version>The mod's semver. Apps can warn on incompatible versions before connecting.

Active discovery

For fastest startup, send the UTF-8 text payload DISCOVER to UDP port 11421. The mod replies directly to the sender with the ROR2SYNC:<host_ip>:<websocket_port>:<mod_version> payload above.

pythonimport socket

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_BROADCAST, 1)
sock.settimeout(1.0)
sock.sendto(b"DISCOVER", ("255.255.255.255", 11421))
data, addr = sock.recvfrom(256)
print(data.decode("utf-8", errors="ignore"))

Passive beacon

The mod sends each passive beacon twice for routing compatibility:

  • Multicast — to 239.255.255.250:11421. Works on routers that block broadcast (like Deco mesh systems).
  • Subnet broadcast — to the local subnet's broadcast address. Works on simple home networks.

Apps only need to receive one or the other. The simplest listener:

pythonimport socket

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
sock.bind(("", 11421))

# Optional: join multicast for routed networks
mreq = socket.inet_aton("239.255.255.250") + socket.inet_aton("0.0.0.0")
sock.setsockopt(socket.IPPROTO_IP, socket.IP_ADD_MEMBERSHIP, mreq)

while True:
    data, addr = sock.recvfrom(256)
    text = data.decode("utf-8", errors="ignore")
    if not text.startswith("ROR2SYNC:"):
        continue
    parts = text.split(":")
    if len(parts) != 4:
        continue
    _, host_ip, ws_port, mod_version = parts
    print(f"Found mod at ws://{host_ip}:{ws_port}/ (v{mod_version})")

Reconnection strategy#

The server doesn't push events you missed during a disconnect, but they aren't gone — the run journal keeps the current run's history queryable. This section covers the socket-level mechanics; the step-by-step catch-up flow is Reconnect pattern. Recover by fetching current state, then optionally replaying the gap:

on socket close:
    wait backoff_seconds (start 1s, double up to 30s)
    reconnect
    wait for hello
    re-send request_world_state to refresh current state
    if your app shows a timeline: send request_run_journal
        with since_sequence = the last sequence you saw,
        to replay the events you missed
    if you were mid a *_items stream when disconnected, re-send the request
Notes
  • sequence resets across mod restarts, not across socket reconnects. If you reconnect to the same running mod, the next sequence continues from where the server left off.
  • run_id is stable for the whole run, so reconnecting mid-run lets you continue tracking the same run.
  • Missed events aren't pushed again, but they are retrievable. A pickup_granted that fired while you were offline won't redeliver on its own — the next inventory_update has the updated inventory, and request_run_journal can replay the event itself. Only the current/last run is queryable; older runs are gone.

Multi-client behavior & rate limits#

The mod supports many simultaneous clients without coordination:

Message kindGoes to
Broadcasts (inventory_update, run_started, pickup_granted, etc.)Every connected client
Caller-only responses (pong, run_summary, loadout_response, etc.)Only the client that asked — except the run-end run_summary push, which goes to every client
Streamed dump responses (modded_items_start … _end)Only the client that asked

Requests are rate-limited per client, per type, each on an independent counter — your overlay and your Discord bot can both connect and both spend their own budget, and a reconnect can fire several different requests back-to-back without one throttling another. Over-limit requests get an error reply with retry_after_ms instead of silence.

RequestLimitWhy
request_world_state1 / secForces a full world scan on the host's main thread.
request_run_journal1 / secWalks the whole journal buffer; responses can be large.
request_challenges1 / 5 secWalks the entire achievement catalog.
request_modded_items1 / 10 secThe heaviest request served: it PNG-encodes every modded icon through the GPU, which has to happen on the game thread.

Everything else (ping, request_run_summary, request_loadout) is cheap and unlimited. Independently of these limits, the host caps how many queued requests of one type it will service per broadcast tick; a client that floods the socket gets the excess dropped rather than answered, so pace your requests instead of queueing them in bulk.

Common mistakes#

Symptoms you'll hit while building, and what's actually going on. The pre-flight version of this list — read before you start rather than while debugging — is Things to know before you start.

  • Connecting to the wrong port. WebSocket is 11420, UDP discovery is 11421.
  • Assuming an inventory_update at title screen. It won't arrive — state is "menu". Send request_world_state for a snapshot.
  • Treating sequence as unique-per-client. It's process-monotonic — gaps are normal.
  • Reconstructing state from events after reconnect. Fetch current truth with request_world_state first; use request_run_journal (with since_sequence) only to backfill your timeline, not to rebuild inventory.
  • Spamming request_world_state. Rate-limited 1/sec per client; the extras come back as rate_limited errors, and a large burst can additionally be dropped by the host's per-tick service cap. Honor retry_after_ms rather than retrying immediately.
  • Hardcoding capabilities. Always feature-detect against hello.capabilities.

Hosting vs joining (multiplayer fidelity)#

The mod reads the game on the machine it's installed on — and Risk of Rain 2 is server-authoritative. Stack buckets (Seekers of the Storm)

SOTS splits every held item stack into three buckets: permanent (normal pickups), temp (decaying temporary items), and channeled (items borrowed while a share effect is active — overwhelmingly the Drifter's Hoard tether). The count field is the gameplay-effective total — permanent + temp + channeled — exactly what the in-game HUD shows.

To keep the wire compact, the breakdown sub-fields appear only on per-player inventory refs (inventory_update.players[].items), minion bot inventories (world.minions.by_owner[].bots[].items), and on pickup_granted.item, and only when the stack isn't plain — i.e. when permanent != count or any temp/channeled copies exist. A vanilla item with no temp/channeled stacks omits all of them: just read count. They never appear on world refs (shop_items, printer_items, ground_items), shop terminals, or chest/shrine pickup previews. On pickup_granted the breakdown describes just the grant that fired (so count == permanent + temp + channeled for that grant), letting you tell a temporary-item pickup from a permanent one.

  "permanent":  2,          // 2 you keep...
  "temp":       2,          // ...plus 2 decaying copies (ceil of the raw temp value)
  "temp_decay": 0.63,       // fractional part of the raw temp value, in [0,1)
  "...":        "..."
}

temp_decay is the fractional part of RoR2's internal raw temp value (raw − floor(raw)), and temp is its ceiling. So a raw value of 1.63 reads as temp: 2, temp_decay: 0.63. As the temp items decay the raw value falls, so temp_decay counts down toward 0; when it reaches an integer boundary a stack drops. It's a progress indicator for the soonest-to-expire stack, not a per-stack timer — RoR2 doesn't expose remaining seconds, only this normalized value.

Timer#

The run clock. run_seconds is how long the whole run has lasted; stage_seconds is how long you've been on the current level. Both freeze whenever the game is paused (is_paused tells you when).

{
  "run_seconds":            247.5,
  "stage_seconds":          42.3,
  "difficulty_coefficient": 1.45,
  "is_paused":              false,
  "has_focus":              true
}
run_secondsTotal in-run elapsed time. Freezes when is_paused is true.
stage_secondsTime on the current stage. Freezes when is_paused is true. Resets to ~0 on each stage_changed.
difficulty_coefficientActual scaling multiplier — 1.0 at start, grows with run_seconds
is_pausedTrue whenever run_seconds isn't advancing — for any reason. See semantics below.
has_focusTrue while the RoR2 game window is the OS focus target. Pair with is_paused to distinguish user-paused from alt-tab pause — see table below.
Use it for:
  • A live run timer or speedrun-style split display
  • Dimming or pausing your overlay when is_paused goes true
  • Pacing stats like "items per minute" (pair with pickup_granted)
  • Telling a real pause from an alt-tab — pair with has_focus (see below)

Timer behavior

What you can rely on:

  • run_seconds is the raw RoR2 stopwatch value. The mod emits whatever Run.instance.GetRunStopwatch() reports at the moment of each broadcast — no smoothing, no clamping. Most of the time it advances monotonically, but the underlying stopwatch can drift backward by a few milliseconds at fixed-time / unscaled-time boundaries. Treat each broadcast value as the authoritative answer and re-sync to it; that's correctness over smoothness.
  • stage_seconds is always present while state == "in_run". Computed as run_seconds − run_seconds_at_stage_start. Resets to ~0 on each stage_changed.
  • is_paused: true whenever the stopwatch isn't advancing — for any reason. The mod derives is_paused empirically by comparing the stopwatch delta against wall-clock delta between broadcasts: if run_seconds isn't moving forward, the timer is paused. That single rule covers every freeze condition — the ESC pause menu, the Bazaar Between Time, RoR2's singleplayer focus-loss auto-pause, the dev console, in-game cutscenes, and any future mechanism that freezes the official run timer. There is a small one-tick latency (one broadcast interval — ~500ms at the default cadence) before a transition is reflected. To tell why the game is paused, pair is_paused with has_focus:
    is_pausedhas_focusMeaning
    falsetrueNormal play
    truetrueUser opened pause menu / entered Bazaar
    truefalseFocus-loss auto-pause (alt-tab in singleplayer)
    falsefalseMultiplayer alt-tab — game doesn't auto-pause
    Companion overlays generally want to treat the "alt-tab auto-pause" row as not paused for UI purposes: the user tabbed over to look at your overlay, not to step away.
  • Broadcasts continue while the game is paused and while the window is unfocused. When is_paused: true, run_seconds and stage_seconds freeze at their last value and the broadcast keeps firing at the configured cadence with those frozen numbers. Use the steady stream of is_paused: true messages as your "game is paused" signal — don't infer pause from absence of broadcasts. The mod forces Application.runInBackground on precisely so the feed survives an alt-tab: the whole point is that your app keeps updating while the player is looking at it instead of the game.
  • Broadcast cadence defaults to 500ms (2Hz) and is host-configurable (100–5000ms). At the default, max staleness of run_seconds at receipt is ≤500ms. The active cadence is published in hello.broadcast_intervals.inventory_update_ms — read it rather than hardcoding.

Apps that want a sub-broadcast-tick smooth timer should:

  1. Read run_seconds from each broadcast as the authoritative value
  2. If is_paused: false, extrapolate forward locally using wall-clock time between broadcasts
  3. If is_paused: true, stop extrapolating and show the frozen value
  4. On the next broadcast, snap to the authoritative value. Occasional small backward corrections (~ms) are normal — that's the stopwatch self-correcting, and the right thing to do is honor it.

Player#

A lightweight "who did this" tag attached to events. It's enough to identify the player and show their name and survivor — but not their full inventory. Think of it as the event's name badge; when you need their items and stats, look them up in the matching PlayerRecord.

Carried by every player-affecting journalable event (pickup_granted, player_died, chest_opened, shrine_used, purchase_made, …). The block that lets your app key per-player state on a stable id.

{
  "display_name":    "ExamplePlayer",
  "network_user_id": "76561198...",
  "is_local":        true,
  "is_bot":          false,
  "resolved":        true,
  "owner_network_user_id": "76561198...",  // minions only — the owning player
  "survivor": {
    "name":      "Bandit",
    "body_name": "Bandit2Body"
  }
}
display_nameResolved display name. Drifts (Steam name changes); do not use as an identity key.
network_user_idStable primary key. For real players this is the Steam ID (or platform equivalent). For bots / NetworkUser-less modded characters, it's a synthetic id prefixed "bot:" built from a stable runtime id (master/body netId or instance id). Never an ordinal that could drift on respawn.
is_localTrue if this player is local to the host (the machine running the mod). Useful for "is this me from the host's PoV" detection on a host-side overlay.
is_botTrue if a character was identified and it has no associated NetworkUser. Drone-style helpers and modded bot survivors land here. network_user_id will use the "bot:" fallback when this is true. Meaningless when resolved is false — see below.

owner_network_user_idPresent only when is_bot and this character is a player-owned minion (drone, turret, guard, …): the network_user_id of the owning player. Use it to attribute a bot's event to its human. Omitted for human players and ownerless characters.
survivorBest-effort. null if the body hasn't spawned yet (very early in a run) or if the body went away before the event fired. body_name is the prefab name with the (Clone) suffix stripped.
Identity rule Always join on network_user_id. The bot fallback format may change in future versions but stays stable within a run, so it's safe for in-session keying.

When is player null, and what is resolved?

player is null only on chest_opened, and only for a chest that dropped without a tracked player interaction (auto-opens, event-driven drops). Every other player-affecting event always carries a Player block — never null.

But a block that exists isn't necessarily identified. If a hook fires without a usable interactor, you get a well-formed placeholder rather than a missing field, and resolved: false marks it: display_name: "?", network_user_id: "", survivor: null.

Gate identity UI on resolved When it's false, is_bot and is_local are not claims about anyone — the mod failed the lookup, so it reports neither bot-ness nor locality. Reading them anyway is how an unidentified human ends up wearing a "BOT" badge. Check resolved before name badges, you-vs-bot labels, or keying per-player state; an empty network_user_id is "unknown actor" and must never be used as a join key. This is rare — vanilla supplies an interactor on all these paths — but it's cheap to get right and silently wrong if you don't.

Balances#

How much run currency the acting player had left immediately after a spend. Attached to the three events that cost something, so you can show "…and they're down to 87 gold" without doing your own bookkeeping.

On purchase_made, chest_opened and shrine_used.

{
  "gold":       87,
  "void_coins": 0
}

Sampled after the spend settled, so it's the balance left over having paid the event's cost. For chest_opened it's captured when the chest was paid for, not when it dropped — the drop is deferred, and by then unrelated gold may have come in.

Both currencies are always present because purchases can be priced in either (see purchase.currency); an item-cost printer purchase leaves both unchanged, which is correct. Lunar coins are deliberately excluded — they're cross-run profile currency, not run state, and the protocol keeps them out for the same reason PlayerRecord does. null when the balance couldn't be read, and on a chest_opened with no tracked payer.

Use it for:
  • A per-event "gold after spend" chip on a run timeline — exact, and correct after a reconnect
  • Reconstructing an economy curve from the journal alone, with no live sampling
  • Spotting when a purchase left the player broke
Why this exists Stamping the next inventory_update balance onto a pending event works live and breaks on reconnect: journal-backfilled events have no adjacent balance sample, so the numbers come out wrong exactly when a user reloads history. This field makes it exact in both paths.
Use it for:
  • Attributing events — who died, who grabbed the legendary
  • Putting a name + survivor next to each entry in a timeline
  • Joining an event back to that player's full PlayerRecord via network_user_id

Mocking the protocol#

You can build and test your app without RoR2 running. Two patterns work well:

1. Replay captured files into your message handler

The cheapest mock: read JSON files and feed them to your message-handling logic as if they came from a WebSocket. Especially useful for unit tests on message reducers.

pythonimport json
from pathlib import Path

def handle(msg):
    # Your real app's message handler
    ...

for name in ["hello", "inventory_update", "pong"]:
    msg = json.loads(Path(f"examples/{name}.json").read_text())
    handle(msg)

2. Minimal fake WebSocket server

For end-to-end tests, spin up a tiny fake server that sends hello and a couple of captured payloads.

pythonimport asyncio, json, websockets
from pathlib import Path

def load(name):
    return Path(f"examples/{name}.json").read_text()

async def handler(ws):
    await ws.send(load("hello"))
    await asyncio.sleep(0.1)
    await ws.send(load("inventory_update"))
    async for msg in ws:
        req = json.loads(msg)
        if req["type"] == "ping":
            await ws.send(load("pong"))
        elif req["type"] == "request_world_state":
            await ws.send(load("inventory_update"))

async def main():
    async with websockets.serve(handler, "127.0.0.1", 11420):
        await asyncio.Future()

asyncio.run(main())
Tip Separate transport (the WebSocket) from your reducer (the code that turns messages into UI state). With that split, you can unit-test the reducer with captured JSON files and integration-test the transport against either the real mod or a fake server.
